# Burrow for Android

A Capacitor 8 shell around the Burrow web UI, the Android sibling of
`clients/ios` (task 01a10d8e). The web UI runs in the WebView; native code
covers what the web cannot reach: sign-in, push (stage 3), the share target
and widgets (stage 4).

| What | Value |
|---|---|
| Package / applicationId | `com.koboai.burrow` (release), `com.koboai.burrow.debug` (debug). **No hyphen**: Android package names cannot contain one, so this is not iOS's `com.kobo-ai.burrow`. Permanent once uploaded to Play. |
| App name | Burrow |
| Min / target / compile SDK | 26 / 36 / 36 (26 rather than Capacitor's 24 for `java.util.Base64`, font variations and adaptive icons without PNG fallbacks) |
| Login callback | `burrow://auth/callback` |

## Rig (moon)

Android builds and the emulator run on **moon** (Linux, `/dev/kvm`), never on
hive. Rock has no JDK and cannot build. Everything the rig creates is named
`burrow-android-<RIG_PREFIX>-*` (default prefix `01a10d8e`); it never touches
another container.

```sh
# from the dev box (rock): copy clients/android to moon
clients/android/scripts/rig/rig.sh push

# on moon (ssh dev@build-host.local), from /srv/dev/android-rig/01a10d8e:
clients/android/scripts/rig/rig.sh build-image      # image + SDK packages (once)
clients/android/scripts/rig/rig.sh gradle testDebugUnitTest
clients/android/scripts/rig/rig.sh gradle ktlintCheck lintDebug
clients/android/scripts/rig/rig.sh gradle assembleDebug
clients/android/scripts/rig/rig.sh emulator-up 35    # or 32 (pre-13 notification path)
clients/android/scripts/rig/rig.sh adb install -r /work/clients/android/android/app/build/outputs/apk/debug/app-debug.apk
clients/android/scripts/rig/rig.sh adb exec-out screencap -p > shot.png
clients/android/scripts/rig/rig.sh emulator-down
```

- The image (`scripts/rig/Containerfile`) is `eclipse-temurin:21-jdk` plus
  node 22 and the Android cmdline-tools. `build-image` installs the packages
  in `scripts/rig/sdk-packages.txt` (platform 36, build-tools, emulator,
  `system-images;android-35;google_apis;x86_64` and `...android-32...`) into
  the named volume `burrow-android-sdk`; Gradle's cache is the volume
  `burrow-android-gradle`.
- Containers run `--device /dev/kvm --network host`. The emulator is
  headless (`-no-window -no-audio -no-boot-anim -gpu swiftshader_indirect`)
  on console port 5654 with the adb server on 5137, off the defaults so the
  rig never meets another emulator or adb.
- `gradle` runs `npm ci` when `node_modules` is missing and `npx cap sync
  android` before every build.
- The work dir is mounted at `/work` in every rig container, so paths
  under `/work/...` reach `adb install`; `rig.sh adb exec-out ...` streams
  stdout back out.

## Push

Every push is **data-only** FCM (`Platform.Push.Notification.to_fcm_payload/1`):
the app builds each notification itself, foreground or not.

| File (`push/`) | Does |
|---|---|
| `PushPayload.kt` | Parses the FCM data map (string values, every key but `kind` optional, blank = missing; ids that are not id-shaped are dropped). Group keys `mentions:<install_host>:<space_id>` and `approvals:<install_host>`; summaries `N new in {space}` and `N approvals`. **The Open guard** `safePath`: only a path starting with exactly one `/` (no `//`, `/\`, whitespace or control characters) is loaded; anything else opens `/`. The app never rebuilds a URL from a slug. |
| `NotificationChannels.kt` | Two channels, Mentions and Approvals (high importance, canvas copy), per install host. Created for signed-in installs only; with two or more signed in, each pair moves under a group named for its install. |
| `NotificationPresenter.kt` | Mentions: MessagingStyle (conversation = space, sender = author), Reply (RemoteInput, `Message {space}`) and Open. Approvals: standard style, Open only. Anything else: tap opens. Colour never set; small icon the status-bar arch. Reply's PendingIntent is the only `FLAG_MUTABLE` one; every notification has its own tag, request codes and data URI. |
| `ReplyReceiver.kt` | `goAsync()`, 4 s + 4 s timeouts, `POST /api/app/spaces/<space_id>/messages` with `text` and `reply_to=<message_id>` (never a thread field; the server picks top-level or in-thread) on the payload's install's bearer. Always re-posts: sent appends `You: {reply}`; failed shows `Couldn't send. Tap to open.` with the error icon and keeps the reply (the web composer has no prefill parameter), and is not cancelled by the tap. |
| `BurrowMessagingService.kt` | `onMessageReceived` -> `NotificationPresenter.present`; `onNewToken` re-registers silently on every signed-in install when notifications are on. Logs nothing. |
| `PushRegistrar.kt` | Token, then `POST /api/app/devices` `{token, platform: "android", package_name, app_install_id}`. Success ONLY on 2xx; a transport failure retries after 0.5 s, 2 s, 5 s; a status is never retried. |
| `PushPermission.kt` | `pushState`: `granted` when notifications are on; `prompt` on Android 13+ until this device has shown the explainer; `denied` otherwise. The flags live in the prefs file `burrow_push`, excluded from backup, never on the server (the web banner's dismissal is per user, PR #1190). |
| `PermissionExplainerActivity.kt` | Canvas 01a10d91 copy: first ask (Turn on notifications -> system prompt; Not now) and denied permanently (Open settings -> `ACTION_APP_NOTIFICATION_SETTINGS`). |
| `PushTokenSource.kt` | Firebase when the build has a default FirebaseApp; otherwise the build type's fallback. |
| `src/debug/.../DebugTokenSource.kt` | Debug only: a stable fake FCM-shaped token from the app install id, for a dev server and `fcm_stub.py` without Firebase. |
| `src/debug/.../DebugPushReceiver.kt` | Debug only, exported to holders of `DUMP` (the adb shell): replays an FCM payload. |

**enablePush** (Android 13+, not yet allowed): explainer, then the system
prompt, then the token, then the POST. It resolves `{registered: true,
state: "granted"}` only on a 2xx, `{registered: false, state: "denied"}` on
Not now or a denial, and rejects `not_signed_in`, `token_failed` or
`registration_failed`. The web hook (`push_subscribe.js` `mountNative`)
calls it on mount when the state is `prompt`; that call IS the first-launch
ask, so there is no second native trigger and two prompts never stack.
After that first ask `pushState` reports `denied` (Not now or a denial), so
the hook never re-asks on a relaunch and nothing re-asks on a timer.
Re-asking happens only from the web's settings row on `/inbox`: the hook
sends `native_platform: "android"` beside the state, and inside the app the
row's `denied` variant carries a "Turn on notifications" button (no browser
address-bar steps). Its click calls `enablePush`, which shows the explainer,
then Android's prompt while Android still allows one, then the "Notifications
are off for Burrow" variant with Open settings once it does not. Below
Android 13 there is no explainer and no prompt.

**Open**: `MainActivity` switches to the payload's `install_host` if it is
not the one showing and loads `https://<install_host><url>` after the
handoff. An install no longer on the phone just brings the app forward.

**Replay a push on the emulator** (debug build; the payload is what
`fcm_stub.py` records, a `{"data": ...}` object, or the bare data):

```sh
P=$(printf '%s' '{"data":{"kind":"chat_mention","title":"Harper in Ops","body":"@Marlowe ping","url":"/chat/ops?message=m1","space_id":"s1","message_id":"m1","install_host":"suite.example.com","author_name":"Harper","space_name":"Ops"}}' | base64 -w0)
rig.sh adb shell am broadcast -a com.koboai.burrow.debug.PUSH \
  -n com.koboai.burrow.debug/com.koboai.burrow.push.DebugPushReceiver --es payload "$P"
```

Debug-only extras for an emulator that cannot sign in (the IdP is
passkey-first): `--es reply_stub 201` (or `500`) on the replay broadcast makes
every `/api/app` call in that process answer with that status and a stand-in
bearer, in-process, so Reply's sent and failed states can be shown. The
explainer is startable from the adb shell through the `DebugExplainer`
activity-alias (DUMP again):

```sh
rig.sh adb shell am start -n com.koboai.burrow.debug/com.koboai.burrow.push.DebugExplainer \
  --es com.koboai.burrow.push.VARIANT ask    # or denied_permanently
```

**Group summaries count every OTHER child plus one.** `notify` is
asynchronous on a device: measured on the API 35 emulator, three approvals
first summarised as "2 approvals", because the child just posted was not yet in
`activeNotifications`. Robolectric posts synchronously and could not show it.
Also, a child that is heads-up is shown outside its group until the heads-up
ends, so a group looks ungrouped for a few seconds after an alert.

**Mutation probes (stage 3, on moon).** Each mutant was applied to the moon
copy and the named test class run; a no-op control edit stayed green. All
killed: Open guard allowing `//host` or an absolute URL (PushPayloadTest);
a non-2xx counted as registered, `outcome` mapping a failure to Registered, or
`send` accepting any status (PushRegistrarTest); `reply_to` renamed to
`thread_id`, an extra `thread_id`, or `reply_to` set to the space id
(ReplyTest); a failed reply not updating the notification (ReplyTest); Reply's
PendingIntent made immutable (NotificationPresenterTest); the debug receiver
declared in the main manifest (ReleaseManifestTest); pushState ignoring the
explainer flag (PushPermissionTest).

## Share

`share/ShareActivity` is a translucent activity (`taskAffinity=""`,
`excludeFromRecents`) holding the ACTION_SEND / SEND_MULTIPLE filters
(`text/plain`, `image/*`, `application/pdf`, `*/*`), so the sheet sits over
the sending app. The filters are not on MainActivity, which would bring the
WebView task forward (canvas 01a10d91 wins over the ticket here).
`ShareSheetModel` mirrors iOS: the space list comes from `GET /api/app/spaces`
on the selected install's bearer, with an optional agent and a message. Each
file is one multipart `POST /api/app/spaces/<id>/messages`, with `text` (the
message, then any shared link) and `agent_id` on the FIRST request only. A
retry after a partial failure sends only the files that are left.

**Size limit.** A file is over when it is larger than
`SizeCheck.MAX_SHARE_FILE_BYTES` (8 MiB, the plan's constant) OR when its
request body would pass `MAX_REQUEST_BYTES` (8_000_000). That second number is
the server's real limit: Plug.Parsers' multipart `:length` applies to the whole
body, and it is what iOS uses. With only the 8 MiB check, an 8.2 MB file would
pass and then get a 413. The copy is the canvas's, and it reads "8 MB" either
way.

**Back.** With nothing typed, back closes the sheet. With something typed, it
asks `Discard this share?` (Discard / Keep editing). With no bearer, the sheet
says so and offers Open Burrow.

## Conversations, shortcuts and voice reply

Task 01a116c4. Every chat push (`chat_mention` AND `chat_message`; before this
only mentions were) is a `MessagingStyle` conversation with a sender `Person`,
a Reply and a long-lived conversation shortcut, so Android files it under
Conversations and offers it as a direct-share target.

**When a shortcut is published** (`shortcuts/ConversationShortcuts.kt`; each
publish also refreshes it):

| Trigger | Where | Reports usage |
|---|---|---|
| A chat notification, published BEFORE `notify` so the notification can name it | `NotificationPresenter.present` | no |
| A message sent from the web view: 01a111bb's `native_donate` with kind `message_sent` (ids only), forwarded by `assets/js/native_donations.js` to `SuiteNative.donate` | `ConversationNoter` (name, kind and path from `GET /api/app/spaces`, cached 10 min per host, one refetch on a miss) | yes |
| A Reply from the notification that the server took (2xx) | `ReplyHandler` | yes |
| A share that was sent | `ShareActivity` | yes |

Every other `donate` kind (`task_created`, `approval_acted`,
`meeting_started`, unknown) resolves and does nothing (`DonateDispatch`).

**Ids.** The shortcut id is `<host>|<spaceId>` (host normalized, space id
`^[A-Za-z0-9_-]{1,128}$`). The notification's `shortcutId` and `locusId` are
that same id. A sender is keyed `<host>|<author_type>:<author_id>` from the FCM
`author_id`/`author_type`, or `<host>|name:<author_name>` when the server sent
no id; the icon is a monogram (the payload carries no avatar URL). A dm
(`space_kind == "dm"`) is a one-to-one conversation, anything else a group. A
redacted push has no `space_id`, so it gets no shortcut; approvals never do.

**Cap.** The launcher allows `getMaxShortcutCountPerActivity()` shortcuts, and
the static `switch_install` counts toward it, so dynamic conversation
shortcuts are capped at `max(0, max - manifestCount)`. The prefs file
`burrow_shortcuts` (excluded from backup) records each id's last use; the least
recently used is evicted first. `switch_install` is never removed and
`removeAllDynamicShortcuts` is never called.

**Removal.** Sign-out (`NativeSignOut`), a revoked bearer (the 401 branch of
`InstallLauncher`) and removing an install in the picker each call
`removeForHost(host)`, which removes the registry ids with the prefix
`"<host>|"` (separator included, so `10.0.2.2` never takes `10.0.2.20`'s) as
both dynamic and long-lived shortcuts.

**Direct share.** Both `shortcuts.xml` files declare an identical
`<share-target>` for `share.ShareActivity` with the category
`com.koboai.burrow.category.SHARE_TARGET`, which conversation shortcuts carry.
A share started from one reads `EXTRA_SHORTCUT_ID`; when it parses and its host
is signed in, the sheet opens on that install with the space preselected.
API 26-28 get no direct-share row (no `androidx.sharetarget` dependency).

**Launch.** A conversation shortcut's intent is `MainActivity` with action
`com.koboai.burrow.action.OPEN_CONVERSATION` and extras host and path
(`/chat/<segment>`). `LaunchRouter` routes it after a notification's Open and
before Switch install, cold and warm, and consumes it; a Recents restore
(`restored`) does not replay it. Measured on the API 35 emulator (2026-10-07):
the launcher starts a dynamic shortcut with `flg=0x10000000` (NEW_TASK only)
and a warm tap reaches `onNewIntent`, unlike the static `switch_install`,
which Android stores with CLEAR_TASK (hence its `SwitchInstallActivity`
trampoline).

**Dependencies.** Built on two branches merged into the task branch, never
rebased: 01a116a1 (Switch install, `LaunchRouter`, `PickerBack`; on main as
#1206) and 01a111bb (`PlatformWeb.NativeDonation`,
`assets/js/native_donations.js`, `author_id`/`author_type` on
`Platform.Push.Notification`). The server half of this task adds only
`space_kind` (FCM payload only; `redact/2` clears it).

## Widgets

`widgets/`: two Jetpack Glance widgets, My approvals (2x1, 2x2, 4x2) and My
tasks (2x2, 4x2), both using `SizeMode.Responsive`. At 4x2 each shows both slabs,
and each slab opens its page (`/inbox`, `/tasks`) through MainActivity's
notification Open path.

- `SlabState` mirrors iOS exactly: SIGNED_OUT with no bearer; STALE when the
  counts are OLDER than 30 minutes (exactly 30 is fresh) or were never loaded;
  otherwise LIVE above zero and ZERO at zero.
- **Cyan means live.** `SlabColors` is the only code that names `burrow_info`:
  it gets `burrow_info` / `burrow_on_info` for LIVE, and `burrow_surface_muted`
  / `burrow_on_surface` for every other state. Both pairs are fixed resources
  (day and night values from colors.xml), never dynamic colour. The widget
  background and label follow GlanceTheme, so they are dynamic on Android 12+.
  `WidgetGuardTest` fails on any other `burrow_info` reference in `res/` or the
  sources.
- `CountsRepository`: `GET /api/app/counts`, cached in DataStore
  (`burrow_widget_counts`) with this device's fetch time. A failed refresh
  keeps the last counts, which then show as stale. Sign-out forgets the host's
  counts.
- `WidgetRefresh`: a WorkManager job every 30 minutes, plus a refresh on app
  foreground, sign-in and sign-out. Each refresh schedules a render just past
  the stale boundary, so the cyan drops on time even when no refresh comes.
- Glance cannot load Public Sans and has no tabular figures, so numerals use
  the system sans in Bold.

Debug-only, for an emulator that cannot sign in: run
`am broadcast -a com.koboai.burrow.debug.WIDGET -n com.koboai.burrow.debug/com.koboai.burrow.push.DebugWidgetReceiver --ez signed_in true --ei approvals 3 --ei tasks 0 --ei age_minutes 0`.
It stores a stand-in bearer and writes the counts. `--ez never_loaded true`
clears the counts; `--ez signed_in false` removes the bearer. The `reply_stub`
on the push replay also answers `GET /api/app/spaces` for the share sheet.

## Login

Why not log in inside the WebView: the install's identity provider is
passkey-first, and WebAuthn does not complete in a third-party app's WebView
(measured on iOS, see `clients/ios/README.md`). A Chrome Custom Tab is the
browser itself, so passkeys and the browser's existing sign-in work there.

1. `AuthSession` makes a PKCE verifier (32 random bytes, base64url) and opens
   `https://<host>/auth/login?app_challenge=<S256 challenge>` in a Custom Tab.
2. The server's OIDC callback redirects to `burrow://auth/callback?code=…`
   (60 s, single use). MainActivity (`launchMode="singleTask"`) receives it
   through its intent filter (scheme `burrow`, host `auth`, path
   `/callback`); `AuthCallback` accepts nothing else.
3. `POST /api/app/session` `{code, code_verifier, app_install_id,
   device_name}` returns `{token, handoff_url}`. A handoff URL on any other
   host is refused.
4. The bearer goes to `KeystoreTokenStore`; the WebView loads `handoff_url`,
   which signs it in.

**Any app can declare the `burrow://` scheme**, so another app could receive
a callback meant for Burrow. **PKCE is what makes an intercepted code
useless**: the server burns a code redeemed with the wrong verifier, and the
verifier never leaves this process's memory. The WebView itself cannot drive
the callback: `NavigationPolicy` blocks `burrow:`, `intent:`, `file:` and
`content:` navigations.

**Relaunch.** `_platform_session` has no `max_age`, so the WebView's session
dies with the process. With a stored bearer, `InstallLauncher` calls `POST
/api/app/handoff` and loads the returned URL, so a cold start needs no
passkey ceremony. A 401 removes the bearer and runs the sign-in.

**Sign-out.** The web "Log out" (`/auth/logout` in the main frame) runs
`NativeSignOut`: `DELETE /api/app/devices/:app_install_id`, `DELETE
/api/app/session` (which also deletes this session's `fcm_devices` rows),
then the Keystore bearer goes, whatever the server answered. The web logout
then runs in the view and the app returns to the picker.

## Bridge on a remote origin

Capacitor Android injects its JS bridge only into its own origin
(`https://localhost`) and accepts plugin messages only from its allowed
origins, so a remote install would not see `window.Capacitor` and
`push_subscribe.js` would never take its native branch. Capacitor's
`server.allowNavigation` is not used: it routes those hosts through
Capacitor's local proxy, which re-issues every request. Instead
`NativeBridgeExposure` adds Capacitor's own bridge script as a document-start
script for the current install's origin only, and re-registers the
`androidBridge` listener with that origin added. Plugin calls from iframes
are still refused. Switching installs moves the exposure to the new origin.

## System bars and back

- Edge to edge (`enableEdgeToEdge()`, transparent bars). Capacitor 8's
  SystemBars plugin handles insets: on Android System WebView 140 and later,
  with `viewport-fit=cover` (root.html.heex has it), the insets pass through
  to the page and `env(safe-area-inset-*)` works; on older WebViews it pads
  the WebView natively and sets `--safe-area-inset-*` to 0. Either way the
  web UI is never under a bar. The web UI reads `env()`, not those variables,
  so nothing extra is injected.
- Status-bar icons follow the page's `data-theme`, as on iOS.
- Predictive back is on (`android:enableOnBackInvokedCallback="true"`): back
  walks the WebView's history (cleared when an install opens, so it never
  walks into the bundled page or another install), then falls through to the
  system's back-to-home.

## Release

`scripts/release.sh` runs from rock (it drives moon over ssh) or on moon
itself:

| Mode | Does | Needs |
|---|---|---|
| `--local` | A debug-signed release AAB. Asserts the applicationId (`com.koboai.burrow`), versionName, versionCode, minSdk >= 26, targetSdk >= Play's floor (35), and that the release manifest has no debug-only component and no cleartext. | nothing secret |
| `--signed` | Builds with `google-services.json` and signs with the UPLOAD key. Checks the AAB's signing-certificate SHA-256 against `upload.crt` and exits 4 on a mismatch. | the files below |
| `--upload` | `--signed`, then `scripts/play_upload.py` to the internal track. `BURROW_PLAY_ARGS=--dry-run` runs every step except the commit, then deletes the edit. | plus the Play key |

- **Secrets.** The script copies them into a `mktemp -d` dir on moon
  (`/srv/dev/android-rig/release-secrets.*`, mode 700). A trap on EXIT,
  INT, TERM and HUP deletes that dir and the copied `google-services.json`.
  - The build reads the keystore and its password by PATH (`rig.sh`
    `RIG_SECRETS`; `app/build.gradle` reads `BURROW_UPLOAD_KEYSTORE` and
    `BURROW_UPLOAD_PASSWORD_FILE`).
  - Nothing prints a secret or passes one in argv.
  - No script here creates a key. Releases are signed only with the existing
    upload key.
- **versionCode.** It comes from the counter
  `/srv/dev/.config/suite-android-build/versioncode` on moon (the last
  uploaded value, plus one). The counter advances ONLY after a committed
  upload. Every other mode builds the next value without consuming it.
- **AAB location.** `~/Dev/build/burrow-android/` on rock and
  `/srv/dev/android-rig/01a10d8e/out/` on moon.
- **Local install test.** `rig.sh bundletool build-apks --local-testing ...`
  then `install-apks`. bundletool 1.18.3 is pinned by sha256 in `rig.sh`.
- **Draft apps.** If the Play app is still a draft, `play_upload.py` retries
  the release as `draft` and says that the first rollout has to be pressed in
  the Console.
- **First upload (stage 5, 2026-10-05).** versionCode 1 (v1.0) went to the
  internal track with status `completed`, and `edits.tracks.get` read it back.
- **No CI job yet.** CI runners on moon are shared, so that is out of scope.
  A CI release would need the upload key as an encrypted secret.

Tests:
- `scripts/test_release.sh` runs on moon from the rig copy. It uses throwaway
  openssl keys and its own counter, and checks:
  - `--upload` with no inputs exits 3 and names each missing path;
  - the `--local` assertions;
  - `--signed` signs with the given key;
  - a mismatched certificate exits 4;
  - no secrets dir is left after success or a forced failure;
  - no secret string appears in the output;
  - no key-generation command and no key material are in the tree.
- `python3 -m unittest scripts/test_play_upload.py` mocks the HTTP layer and
  covers the edit order, the draft fallback, that a dry run deletes the edit,
  and that no credential is printed.
- Mutation-checked: dropping the trap's `rm`, never comparing the
  fingerprint, and echoing the password file are each caught by
  `test_release.sh`.

## Firebase and signing

`google-services.json` and the upload keystore are never committed
(`.gitignore`). They live outside the repo on rock in
`~/private_keys/burrow-android/`. `release.sh --signed/--upload` copies
`google-services.json` into `android/app/` and its trap deletes it; without
it the google-services plugin is not applied and there is no FirebaseApp.

The file lists only `com.koboai.burrow`, so the debug variant
(`com.koboai.burrow.debug`) would fail the plugin's
`processDebugGoogleServices`. `app/build.gradle` disables that task unless the
file names the debug package: a debug build then has no Firebase config and
registers with `DebugTokenSource`. Checked on moon (stage 3) with the real file
present: `processReleaseGoogleServices` ran and wrote `google_app_id`;
`processDebugGoogleServices` was SKIPPED.
