# Burrow as your work AI: what outside assistants can do with Burrow today

Research note, checked 2026-11-07 against core `origin/main` at `edbcfbe3a` and each vendor's current public docs. Every vendor claim links to that vendor's own page. Burrow code is cited as `path:line` on that sha.

## First: is there an Apple API for another AI to talk to Siri directly? No.

Checked 2026-11-07 in Apple's current developer docs. Siri does not offer a way for a third-party AI to converse with it. Apple opened two things, and neither is that:

- **The Siri AI Developer Preview (2026-11-03).** It lets "any app bring its content and actions directly into Siri AI by using App Intents" ([Apple Developer news](https://developer.apple.com/news/?id=gdk2umrf)). Siri calls into an app's actions as tools: a tool "is an AppIntent that Siri can create, configure, and invoke" ([ToolIntent](https://developer.apple.com/documentation/appintents/toolintent)). App skills give Siri guidance for chaining several tools, but cannot "enforce deterministic behavior" ([app skills](https://developer.apple.com/documentation/appintents/orchestrating-complex-actions-with-app-skills)). The preview "isn't available to external testers in TestFlight or to versions of your app that you publish on the App Store" ([Siri AI Developer Preview](https://developer.apple.com/documentation/appintents/siri-ai-developer-preview)).
- **The ChatGPT extension.** A user can switch on ChatGPT inside Siri AI under Settings > Siri > Set Up Extensions ([Apple Support](https://support.apple.com/guide/iphone/use-chatgpt-with-apple-intelligence-iph00fd3c8c2/ios)). It is a built-in Apple integration. Apple's developer docs describe no way for another AI provider to become one.

So the claim holds. Siri reaches Burrow the way it reaches any app: Burrow exposes actions and content, and Siri calls them. Siri is a front door to Burrow, not a peer Burrow can talk to.

## One row per assistant

Connection methods: **App Intents** (Siri calls the Burrow iPhone app), **remote MCP** (the assistant calls Burrow's `/mcp` endpoint), **OAuth connector** (the same, but signed in with OAuth), **none**.

Burrow's `/mcp` endpoint takes a static bearer token and has no OAuth (see "Burrow's side" below). That one fact decides most rows.

## Burrow's side (origin/main at `edbcfbe3a`)

**The MCP endpoint.** One URL, `POST /mcp`, JSON-RPC 2.0 over Streamable HTTP.

- Route: `apps/platform/lib/platform_web/router.ex:1317-1320` (`scope "/mcp"`, `post("/", MCPController, :handle)`, `get("/", MCPController, :stream)`). `GET` returns 405, so there are no server-initiated notifications yet (`apps/platform/lib/platform_web/controllers/mcp_controller.ex:63`).
- Protocol version `2025-06-18` (`mcp_controller.ex:28`). `tools/list` returns the caller's effective tools (`mcp_controller.ex:79-84`); `tools/call` runs through one path, `ToolCall.invoke/3` (`mcp_controller.ex:99`).
- The same tools are also served over the `/runtime/ws` WebSocket used by the channel plugins; both transports ask `Platform.Federation.ToolAuthorization`, so they cannot answer differently (`mcp_controller.ex:12-16`).

**Auth for outside clients.** A static bearer token, minted per agent runtime. There is no OAuth for MCP clients.

- The `:mcp` pipeline is `accepts json` plus `PlatformWeb.Plugs.RuntimeBearerAuth` (`router.ex:159-162`).
- The plug reads `Authorization: Bearer <token>`, SHA-256-hashes it and looks it up as `AgentRuntime.auth_token_hash`; only an `active` runtime bound to an agent passes (`apps/platform/lib/platform_web/plugs/runtime_bearer_auth.ex:20-34`). Anything else gets a 401 with a JSON-RPC body (`runtime_bearer_auth.ex:38-48`).
- The token is 32 random bytes (`apps/platform/lib/platform/agents/agent_runtime.ex:110-112`). An owner gets one today by federating an agent in Control Center: the result screen shows the raw token once (`apps/platform/lib/platform_web/live/control_center/onboarding_events.ex:303-311`), and `Federation.generate_runtime_token/1` replaces it (`apps/platform/lib/platform/federation.ex:622-631`).
- No OAuth authorization server, no `/.well-known/oauth-protected-resource` and no dynamic client registration exist. The only `/.well-known` routes are the federation descriptors (`router.ex:1193-1199`). The plug never sends a `WWW-Authenticate` challenge. An outside chat app that requires OAuth for custom connectors therefore cannot connect at all.

**Which tools an outside AI gets.** Its runtime's tool profile, capped by its owner's permissions.

- The core capability bundles are listed at `apps/platform/lib/platform/federation/tool_surface.ex:87` (`canvas messaging task plan review space context_read federation memory skill attachment files meetings mail experiments code_mode prototype access admin voice_ask`). `list_tools/1` expands a profile into tools (`tool_surface.ex:220`).
- A new runtime gets `federation space context_read messaging attachment skill meetings mail` by default (`agent_runtime.ex:37`).
- `Platform.Access.Tools.effective_tools/1` expands the stored profile, then drops every tool whose permission the owner-capped scope does not hold (`apps/platform/lib/platform/access/tools.ex:18-29`). `authorize/2` refuses any tool not in that list (`tools.ex:35-39`). A missing profile row fails closed.
- Calendar read and propose ride the `context_read` bundle (`tool_surface.ex:261`); inbound-mail reads and drafts ride `mail`, and exist only while the mail module is on (`tool_surface.ex:278`, `tool_surface.ex:1248-1249`).

**Permission and audit trail.**

- Every MCP tool call writes a `dispatch_tool_calls` ledger row with its attribution, never its arguments or results (`apps/platform/lib/platform/federation/tool_call_ledger.ex:1-22`, `record/1` at `tool_call_ledger.ex:92`).
- A refused call emits `[:platform, :federation, :tool_call_denied]` telemetry with the runtime id and tool name (`mcp_controller.ex:102-110`).
- The platform audit log is an append-only event table fed from telemetry (`apps/platform/lib/platform/audit.ex:1-24`, `record/1` at `audit.ex:39`, `list/1` at `audit.ex:85`; handler attached at `apps/platform/lib/platform/audit/telemetry_handler.ex:392`). Denied reads (canvas, task) are audited (`telemetry_handler.ex:168-182`).
- Calendar writes from an agent are proposals: they create a tentative hold and an Inbox approval unless the owner pre-approved (`apps/platform/lib/platform/federation/calendar_tools.ex:21-23`).
- What is not there: per-connector consent screens, a "connected apps" list an owner can revoke from, and per-call user attribution. A connected outside AI acts as an agent, not as the human.

**Burrow to Burrow (federation).**

- Install-to-install peers: `apps/platform/lib/platform/federation/peers.ex` (`propose/2` at `peers.ex:304`, `accept/2` at `peers.ex:347`, `revoke/2` at `peers.ex:365`). Revocation is written before the notice is sent, so inbound stops at once (`peers.ex:13-18`).
- Peers publish keys at `/.well-known/burrow-federation` (`router.ex:1198`) and POST Ed25519-signed envelopes to `/federation/v1/inbox` (`router.ex:1207-1209`), behind the `PEER_FEDERATION_ENABLED` switch.

## The three gaps worth building

1. **One-click "Connect ChatGPT, Claude or Gemini".** Add OAuth 2.1 to `/mcp`: protected-resource metadata, an authorization server on Burrow's own login, and dynamic client registration. Add a Settings page listing connected assistants, each revocable, each acting as the signed-in person within that person's scope. This one change unblocks ChatGPT, the Gemini app, Gemini Enterprise and Microsoft 365 Copilot connectors, and turns Claude's copy-a-secret setup into a sign-in.
   *Falsifier:* wrong if a non-developer still cannot connect ChatGPT and Claude to Burrow by pasting one URL and signing in, or if ChatGPT's docs show it accepting a static API key (then a setup page alone would do).
2. **Siri "add to my list".** One sentence ("add send the caterer the menu to my Burrow list") lands on the person's own list from task `01a1b714-f4eb-7000-818f-4e799d71a090` (My list). Build it as a `ToolIntent` on that list's create action, with the reminders-schema trial as the App Store fallback until Apple ships the preview.
   *Falsifier:* wrong if a device test shows Siri cannot fill a usable item from one sentence through either path, or if My list ships without a per-person create endpoint the intent can call.
3. **Forward to your agent.** Give each agent its own inbound address that an owner can forward or filter mail to from Gmail or Outlook without an admin. Mail lands in that agent's space through the existing inbound pipeline. Calendar invites in the mail become calendar proposals.
   *Falsifier:* wrong if an owner can already, with no admin step, point a Gmail filter at an address that reaches a chosen agent. Then this is a setup guide, not a build.
