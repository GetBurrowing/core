# Elixir 1.20.4 `module_definition`: :compiled vs :interpreted (task 01a0fd73 stage 2)

## Decision

module_definition: :interpreted measured 4.87% faster (median cold `MIX_ENV=test mix compile` of
apps/platform, 13.393391186 s vs 14.079414617 s, ratio 0.951275), which is above the 0.85 bar
(a 15% improvement); left off. The default stays "compiled", platform's `elixir: "~> 1.15"`
requirement is unchanged, and the `SUITE_MODULE_DEFINITION` hook and
`scripts/measure-module-definition.sh` stay so a re-measurement on a future Elixir is a command.

Both conditions of the adoption rule fail as measured. (a) fails: 0.951275 > 0.85. (b) also fails
on the literal rule, because the interpreted full suite had one failure that the compiled run did
not (details below). That failure is a wall-clock assertion under load, and it passed 3 of 3 when
re-run alone. It does not affect the decision, because (a) already rejects adoption.

- adoption threshold: 0.85 x 14.079414617 = 11.967502424 s. The interpreted median would have needed
  to be at or below this.
- median deps_compile_s (untimed in the metric, recorded separately): compiled 71.205240226,
  interpreted 68.482367838
- beam_count in `_build/test/lib/platform/ebin`: 949 in every row of both variants. Every timed
  compile printed `Compiling 911 files (.ex)`, so neither variant compiled less.
- In every timed compile, `lib/platform/federation/tool_surface.ex` printed "it's taking more than
  10s". This is an inference, not measured here: the project compile appears bounded by that one
  module's critical path, and `module_definition` changes how module BODIES are evaluated, not how
  function bodies are compiled. That would explain the small gain.

## Run conditions

- Host: test-host, 16 CPUs, shared with GitHub Actions runners and sibling agents' core-test runs.
  load1_before and the count of OTHER running `core-test-*` containers are in every row:
  load1 5.94-7.76, and 0-1 other containers. A sibling full suite (task 01a0fd62) overlapped rounds
  1-2. No row shows an identifiable load spike, so no row was marked invalid.
- Image `localhost/core-test:1.20.4-otp-28-slim-cc`, which prints `Elixir 1.20.4 (compiled with
  Erlang/OTP 28)` in every row. This is the private rig from stage 1; the shared
  `~/bin/core-test.sh` was not touched (sha256 `37b7e807...` throughout).
- CPU pinning used `taskset -c 0-5,8-13`, which podman/crun inherit, as `core-test.sh` does. The plan
  said `podman run --cpuset-cpus`, but on test-host that fails before the container starts:
  `crun: controller 'cpuset' is not available` (exit 126), because the cpuset controller is not
  delegated to the rootless user manager. Inside a taskset-launched container,
  `Cpus_allowed_list: 0-5,8-13`.
- Deps were constant. There was one clone, one `mix deps.get`, and one copy of the rig's hex/mix
  cache. Each run did `rm -rf _build` (apps/platform), then `mix deps.compile`, recorded but not part
  of the metric, then the timed `SUITE_MODULE_DEFINITION=<v> MIX_ENV=test mix compile`, all in a fresh
  container.

## Warm `_build`: does flipping the variant recompile?

Yes, in both directions. So the env var is not a stale-artifact hazard: Mix records
elixirc_options in the compile manifest. `test-host:~/rigs/elixir-1.20.4-01a0fd73/warm-01a0fd73-84481f08-2520413.log`,
all on one warm `_build` in one container:

| step | SUITE_MODULE_DEFINITION | recompiled |
|---|---|---|
| 1 cold | unset | 911 files |
| 2 control, same again | unset | none |
| 3 control | compiled (== unset, since both yield `[]`) | none |
| 4 flip | interpreted | 911 files |
| 5 control, same again | interpreted | none |
| 6 flip back | compiled | 911 files |

The harness's WARM_CHECK step agreed: going interpreted to compiled after the last round printed
`Compiling 911 files (.ex)`. The cost of a flip is one full project recompile, about 14 s.
